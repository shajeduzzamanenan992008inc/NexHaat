# NexHaat AI Feature Integration Guide

## Purpose and status

This guide is the review contract for importing features generated by Google AI
Studio, GitHub Copilot, ChatGPT, Gemini, Claude, or another coding assistant.
It is additive: existing Flask authority, React/Vite UI, Express AI routes,
Firebase compatibility, Android contracts, OTP flows, schemas, and workflows
remain in place.

Phase 17 and Phase 18 are not fully verified: staging browser/API integration
is blocked by the missing approved CORS/test environment, and restore rehearsal
is blocked by the absence of a disposable restore target. New AI features must
not be described as production-ready until those gates are independently
closed where relevant.

## Universal feature intake

Every proposed feature must begin with a completed
`docs/templates/AI_FEATURE_SUBMISSION_TEMPLATE.md` containing:

- unique feature ID and human purpose;
- source AI/tool, source repository/export, framework, runtime, and version;
- frontend components, routes, state, assets, and accessibility behavior;
- backend endpoints, services, repositories, authorization, and error contract;
- data models, migrations, indexes, retention, and schema dependencies;
- required environment variables and secret ownership;
- third-party APIs, network boundaries, timeouts, quotas, and fallback behavior;
- dependencies and lockfile impact;
- conflicts with existing features, routes, clients, or data sources;
- security/privacy requirements and abuse cases;
- tests, acceptance criteria, monitoring, rollout, and rollback instructions.

The feature is not accepted until a reviewer records the inspected paths and
labels each item as `verified`, `inferred`, `blocked`, or `not applicable`.

## Google AI Studio import workflow

1. **Quarantine the export.** Keep generated files outside the production
   source tree or in a review branch. Never copy secrets, `.env` values,
   service-account files, Firebase keys, or credentials.
2. **Inventory before editing.** Identify React/TypeScript/Vite versions,
   CSS/assets, routes, state libraries, direct `fetch` calls, Firebase Auth or
   Firestore usage, mock data, and package dependencies.
3. **Map boundaries.** Map UI components to existing `src/components`,
   `src/pages`, `src/context`, and `src/types`; map marketplace calls to the
   existing Flask client in `src/lib/marketplaceApi.ts` and auth calls to
   `src/lib/flaskAuth.ts`.
4. **Preserve authority.** Flask `/api/v1`, server-side sessions/CSRF,
   authorization, prices, stock, checkout, orders, payments, OTP, and database
   remain authoritative. Generated Firebase or mock state cannot authorize or
   price a marketplace operation.
5. **Preserve useful capabilities through adapters.** Keep Firebase features
   separate until an approved identity-linking design exists. Keep Express
   Gemini/science features behind server-side routes and provider adapters.
6. **Resolve dependencies explicitly.** Compare generated dependencies with
   `package.json`/`package-lock.json`; do not add duplicates or upgrade
   unapproved packages. Use existing components and types where possible.
7. **Review security.** Check secrets, unsafe HTML, input validation, CSRF/CORS,
   IDOR, file uploads, prompt injection, mock-data leakage, direct database
   access, and route collisions.
8. **Integrate in a small batch.** Add a focused adapter/component or a
   compatibility re-export. Do not bulk-copy an entire AI Studio project or
   replace `AppContext`, Flask auth, or the database boundary.
9. **Verify.** Run the smallest relevant tests, then lint/build and the
   applicable Python/Android checks. Browser/staging checks are separate gates.
10. **Document and stage.** Update the feature registry, report changed files,
    known limitations, rollout flag/configuration, and the exact rollback.
11. **Review the diff.** Run
    `python scripts\validate_repository_structure.py`. Any source deletion,
    rename, or move is a human-review item; use `--fail-on-review` when a
    CI/release gate must reject unreviewed changes. The checker reports
    findings and never restores files automatically.

## Existing adapters and boundaries

| Concern | Existing boundary | Rule |
|---|---|---|
| Flask session/CSRF | `src/lib/flaskAuth.ts` | Use credentialed cookies and `X-CSRFToken`; never store session/OTP secrets |
| Marketplace API | `src/lib/marketplaceApi.ts` | Reuse the typed envelope and server-authoritative responses |
| React state/UI | `src/context/AppContext.tsx`, `src/components`, `src/pages` | Preserve guest preview and existing AI Studio behavior during migration |
| Flask authority | `app/api`, `app/routes`, `app/services`, SQLAlchemy models | Keep validation, authorization, price, stock, and state transitions server-side |
| Express AI | `server.ts` | Provider keys stay server-side; output is untrusted and cannot authorize commerce |
| Firebase | `src/lib/firebase.ts`, Firebase config/rules | Treat as a preserved separate capability until account linking is approved |
| Android | Retrofit `ApiService.kt`, DTOs, cookie/CSRF interceptors | Preserve `/api/v1` envelope and additive compatibility |

Do not create a second marketplace API client or a second OTP implementation
without an approved architecture decision.

## AI-generated code safety checklist

- [ ] No secrets, tokens, credentials, private URLs, or customer data added.
- [ ] No `dangerouslySetInnerHTML`/raw HTML without reviewed sanitization.
- [ ] Inputs have schema, length, type, and business validation.
- [ ] Authentication and authorization are server-side and object-scoped.
- [ ] CSRF and narrow CORS behavior are preserved.
- [ ] No direct browser-to-database access or client-authoritative totals.
- [ ] Uploads enforce type, size, signature, storage isolation, and scanning.
- [ ] Mock/demo data cannot silently replace production API data.
- [ ] No duplicate routes, providers, dependencies, or conflicting types.
- [ ] AI output is bounded, validated, and treated as untrusted.
- [ ] Timeouts, rate/cost limits, fallback, logging, and privacy are defined.
- [ ] Tests cover permitted/denied access, failure, retry, and rollback paths.

## Acceptance and rollback

Acceptance requires source inspection, focused tests, `npm run lint`,
`npm run build`, applicable Python tests, and Android tests when the feature
touches those boundaries. Staging, provider, payment, OTP delivery, and
restore evidence must be explicitly marked `NOT TESTED` or `BLOCKED` when
unavailable.

Rollback must remove only the additive feature files, adapter registration,
feature flag/configuration, and tests/docs introduced by that feature. It must
not remove Flask OTP/authentication, Firebase, Express routes, Android DTOs,
database history, or existing UI fallbacks. Schema changes require an additive
forward-compatible migration and a reviewed recovery plan; no destructive
rollback is permitted.

## Change-review command and limitations

```powershell
python scripts\validate_repository_structure.py
python scripts\validate_repository_structure.py --fail-on-review
```

The checker validates registry paths, required documentation/configuration,
simple relative TypeScript import targets, browser marketplace adapter
boundaries, duplicate registry IDs, and changed source deletions/renames
relative to `HEAD` (or `--base <revision>`). It reports the current worktree
for review and does not infer that a deletion is accidental. It does not prove
runtime behavior, detect every dynamic import, resolve Python imports, inspect
GitHub branch protections, or replace human review.
